# Idempotency and concurrency

Step 25 prevents repeated or concurrent commands from duplicating financial or
inventory effects. PostgreSQL RPC functions are the transaction boundary; the
application does not split one command across multiple database transactions.

## Command coverage

| Command                   | Retry protection                                                                                                                            | Concurrency protection                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Customer payments         | Business-scoped UUID key and request fingerprint return the original payment for an identical retry.                                        | Request and customer advisory locks plus locked outstanding purchase rows prevent over-allocation.                   |
| Supplier payments         | Business-scoped UUID key and request fingerprint return the original payment for an identical retry.                                        | Request and supplier/currency advisory locks plus locked outstanding purchase rows prevent over-allocation.          |
| Customer credit purchases | A server-generated UUID is stored in the private command registry with its fingerprint and result ID.                                       | An advisory transaction lock serializes requests using the same key.                                                 |
| Supplier purchases        | A server-generated UUID fingerprints supplier, destination, currency, rate, and every normalized product line.                              | An advisory transaction lock serializes the payable, value receipt, product lines, and quantity receipts atomically. |
| Daily sales close         | Closing an already closed record returns its active closure. Unique closure sequence and ledger-source constraints block duplicate effects. | Business/day advisory locks and row locks serialize draft saving, closure, and automatic day rollover.               |
| Expenses                  | Business-scoped UUID key and fingerprint return the original expense.                                                                       | The request advisory lock serializes retries; the RPC writes expense, ledger, and audit rows atomically.             |
| Inventory transfers       | Business-scoped UUID key fingerprints the normalized product lines and returns the original movement.                                       | Request, product, and location locks serialize quantity/cost checks and all warehouse-to-shop effects.               |
| Stocktakes                | Business-scoped UUID key and fingerprint return the original stocktake.                                                                     | Request and location advisory locks serialize expected-balance calculation and adjustment creation.                  |
| Product stock movements   | Business-scoped UUID key and request fingerprint return the original immutable movement.                                                    | Request and business/product advisory locks serialize derived-balance checks, inserts, and reversals.                |
| Product sales             | Business-scoped UUID fingerprints the normalized product lines, selling prices, payment split, customer, and notes.                         | Request, day, and stable product locks serialize stock/cost checks, sale lines, receivable, and daily totals.        |
| Sale returns              | Business-scoped UUID fingerprints original sale lines, quantities, dispositions, refund split, and reason.                                  | Request, sale, customer, and product locks prevent excess returns, credit reductions, and conflicting stock effects. |
| Inventory exceptions      | Business-scoped UUID fingerprints product, location, type, quantity, and required administrator reason.                                     | Request and product locks serialize weighted-cost lookup, stock deduction, inventory value, and damaged quantity.    |
| Reversals                 | A repeated reversal fails safely because the preserved source row is already marked reversed.                                               | Each reversal locks its source row before checking status and creating the compensating effect.                      |

## Request lifecycle

Important create forms receive a UUID generated by the server-rendered page.
The UUID is submitted in a hidden `idempotencyKey` field and validated before
the RPC runs. The database fingerprints all command inputs, acquires a
transaction-scoped advisory lock, and then:

1. returns the original result when the key and fingerprint match;
2. rejects the key when the fingerprint differs; or
3. creates all financial, inventory, and audit effects and stores the result in
   the same transaction.

A failed transaction stores neither its result nor its key, so a corrected
retry can execute normally.

## Allocation and close invariants

Customer and supplier payment functions serialize by debt owner and lock the
eligible purchase rows before calculating remaining balances. Concurrent
payments therefore cannot both consume the same outstanding amount.

Daily close locks the business/day workflow and the sales row. Database
constraints allow one active closure sequence and one original ledger effect
per closure source, so two close requests cannot duplicate cash or bank
inflows.

## Tests

Runtime database tests cover identical retries, changed-payload key reuse,
duplicate close attempts, allocation totals, and rollback behavior. The Step 25
database audit additionally verifies required keys, advisory/row locks,
protected purchase RPC permissions, and close uniqueness constraints.
